# Quiz 03 — Dirty page는 게으르게 쓰인다 (lazy write)

## 시나리오

2,000행짜리 테이블 전체를 `UPDATE`하고 **COMMIT까지 완료**한다(autocommit).
그 직후 데이터 페이지 카운터를 관측한다.

- `Num_data_page_dirties` — 페이지를 dirty로 표시한 횟수 (누적)
- `Num_data_page_iowrites` — 데이터 페이지를 실제로 디스크에 쓴 횟수 (누적)
- `Num_data_page_dirty` — 지금 이 순간 버퍼 안의 dirty 페이지 수 (게이지)

## 실행

```bash
./run.sh
```

## 문제 (4지선다)

`UPDATE ... ; COMMIT` 완료 직후, 이번 트랜잭션이 수정한 데이터 페이지 중
**디스크(데이터 볼륨)에 이미 써진 것**은 대략 몇 장일까?

- **(a)** 전부 — COMMIT은 수정된 데이터 페이지를 모두 디스크에 쓰는 것이다.
- **(b)** 보통 **0장** — 수정 페이지들은 버퍼 안에서 dirty로 남아 있고, 나중에 쓰인다.
- **(c)** 인덱스 페이지만 — 데이터 페이지는 남고 인덱스는 즉시 쓰인다.
- **(d)** 절반 — COMMIT은 절반을 쓰고 나머지는 백그라운드에 맡긴다.

> 힌트: COMMIT이 durability를 보장하는 수단이 꼭 "데이터 페이지 쓰기"여야 할까?
